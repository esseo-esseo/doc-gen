이 프로젝트의 변경 사항을 2단계로 리뷰하라.

먼저 다음 문서들을 읽어라:
- `/CLAUDE.md`
- `/docs/ARCHITECTURE.md`
- `/docs/ADR.md`
- 해당 phase의 `phases/*/index.json` (존재하는 경우, 어떤 계획을 따르는지 파악)

---

## Phase 1 — Spec Compliance (스펙 준수)

변경사항이 계획/요구사항대로 구현되었는지 검증한다.

**Phase 1 체크리스트:**
1. **범위 준수**: 계획에 없는 기능이 추가되지 않았는가?
2. **누락 없음**: 계획의 모든 항목이 구현되었는가?
3. **아키텍처 준수**: ARCHITECTURE.md 디렉토리 구조를 따르는가?
4. **CRITICAL 규칙**: CLAUDE.md의 CRITICAL 규칙을 위반하지 않았는가?

| 항목 | 결과 | 비고 |
|------|------|------|
| 범위 준수 | ✅/❌ | {상세} |
| 누락 없음 | ✅/❌ | {상세} |
| 아키텍처 준수 | ✅/❌ | {상세} |
| CRITICAL 규칙 | ✅/❌ | {상세} |

**Phase 1에서 ❌가 있으면 Phase 2로 넘어가지 말고 먼저 수정하라.**
Spec 위반은 코드 품질 문제보다 항상 우선순위가 높다.

---

## Phase 2 — Code Quality (코드 품질)

Phase 1을 완전히 통과한 뒤에만 진행한다.

**Phase 2 체크리스트:**
1. **테스트 존재**: 새로운 기능에 대한 테스트가 작성되어 있는가?
2. **기술 스택 준수**: ADR에 정의된 기술 선택을 벗어나지 않았는가?
3. **빌드 가능**: 빌드 명령어가 에러 없이 통과하는가?
4. **코드 품질**: 중복 코드, 불필요한 복잡성, 명백한 버그가 없는가?

| 기술 스택 준수 | ✅/❌ | {상세} |
| 빌드 가능 | ✅/❌ | {상세} |

## 최종 판정

| 상태 | 조건 |
|------|------|
| **APPROVED** | Phase 1 + Phase 2 모두 ✅ |
| **BLOCKED** | Phase 1 ❌ — Spec 위반 수정 후 재리뷰 |
| **CHANGES REQUESTED** | Phase 2 ❌ — 품질 개선 후 재리뷰 |

위반 사항이 있으면 수정 방안을 구체적으로 제시하라.
